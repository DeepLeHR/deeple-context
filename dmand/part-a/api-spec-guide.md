# API 스펙 작성 가이드

API 스펙은 백엔드와 프론트가 같이 보는 구현 계약이다. 아래 순서로 짧고 명확하게 작성한다.

## 기본 규칙

- BE가 판단하는 것과 FE가 보여주는 것을 분리한다.
- FE가 직접 계산하면 안 되는 값은 명시한다.
- 요청 후 BE가 다시 검증하는 항목을 적는다.
- 시나리오별 FE 사용 흐름을 적는다.
- 저장, 상태 변경, 이력 보존이 있으면 적는다.

- BE가 최종 판정해서 내려주는 값
- FE가 직접 판단하면 안 되는 값
- null 또는 빈 배열의 의미
- fallback 기준

4. FE가 다음 요청에 어떤 값을 보낸다.

## 최소 작성 항목

작은 API라도 아래는 꼭 작성한다.

- 목적
- 요청 스펙
- 응답 스펙
- FE 사용 흐름
- BE 검증 규칙
- 에러 응답

## 체크리스트

- ID가 DB 식별자라면 number 예시를 썼는가?
- 원화 고정처럼 불필요한 필드를 응답에 넣지 않았는가?
- FE가 직접 판단하면 안 되는 조건을 적었는가?
- BE가 요청 시 다시 검증할 항목을 적었는가?
- 정상/대상 아님/빈 상태 중 필요한 시나리오를 적었는가?
- 저장 또는 상태 변경이 있으면 무엇이 바뀌는지 적었는가?

## 작성 주의

- `FE가 알아서 처리`처럼 책임이 모호한 표현을 쓰지 않는다.
- `적절히`, `필요시`, `상황에 따라`처럼 기준이 없는 표현을 피한다.
- 비즈니스 정책 문서에는 테이블명보다 정책 의미를 적는다.
- API 스펙 문서에는 FE가 구현에 사용할 수 있는 필드와 흐름을 적는다.
