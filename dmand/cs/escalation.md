# CS 에스컬레이션 정책

> 개발팀이나 상위 부서로 이관하는 기준과 프로세스

## 에스컬레이션 기준

| 레벨 | 상황 | 처리 부서 |
|------|------|-----------|
| L1 (CS팀) | 단순 문의, FAQ, 계정/환불 처리 | CS팀 직접 처리 |
| L2 (CS팀 심사) | 복잡한 환불, 멘토링 분쟁, 데이터 정정 | CS팀 심사 후 처리 |
| L3 (개발팀) | 버그/오류 제보, 기능 개선 요청 | 개발팀 (Jira 티켓) |
| L4 (운영/관리자) | 정책 예외, 대규모 장애, 법적 이슈 | 운영팀/관리자 |

## 에스컬레이션 프로세스

1. **정보 수집**: 유저 정보, 문제 상황, 재현 경로, 스크린샷 수집
2. **1차 판정**: CS팀 낶에서 처리 가능 여부 판단
3. **이관 결정**: 처리 불가 시 담당 부서로 이관
4. **Jira 티켓 생성** (개발팀 이관 시): 버그 분석 → 티켓 초안 작성 → 개발팀 전달
5. **유저 안내**: 처리 예상 시간과 다음 단계 안내

## 판단이 애매한 케이스

1. 오류 + 환불 동시 → **버그 처리(cs-bug-handler) 먼저**, 환불은 이후 판정
2. 멘토링 + 환불 동시 → **멘토링 중재(cs-mentoring-mediator) 먼저**
3. 계정 문제로 서비스 이용 불가 → **계정 처리(cs-account-manager) 우선**
4. 내용 불명확 → 어떤 서비스에서 어떤 문제가 발생했는지 먼저 확인

## 개발팀 이관 시 필요 정보

- 유저 식별 (닉네임/이메일)
- 사용 기기 및 OS/앱 버전
- 발생 화면 및 동작
- 관찰된 현상
- 재현 여부 (항상/간헐적/1회)
- 스크린샷/영상
- 결제 유저 여부
